# 五人分工咬合与接口契约

## 1. 分工原则

每人拥有一个端到端业务领域，包含需求、设计、实现、测试、文档与演示。共享基础由A整合，业务规则由各领域负责人维护。成员A–E是建议角色编号，不能视作已发生的五人贡献。

|成员|责任主线|实现落点|必须交付的证据|建议计划权重|
|---|---|---|---|---|
|A 组长/集成|架构、登录、目录缓存、发布|工厂、db、domain、auth、catalog、offerings|领域/架构图、接口基线、安装复现、目录单飞测试|20%|
|B 人员与一致性|学生教授建档、账户同步、历史删除保护|people、registrar、人员模板|校验等价类、CRUD与删除回归、数据字典|20%|
|C 注册核心|草稿、注册、退选、冲突、名额、版本|registration、prereq、student、seats.js|选课顺序图、并发与回滚测试、4+2口径说明|20%|
|D 教学与成绩|授课认领、花名册、成绩、成绩单规则|teaching、professor、成绩展示契约|授课冲突/越权测试、成绩→先修联调|20%|
|E 周期与计费|截止、关闭、备选、取消、发件箱|semesters、closing、billing、admin|状态机、故障注入、账单对账与重试证据|20%|

建议权重仅用于工作量平衡；实际贡献比例据实计算，禁止直接当成最终百分比。

## 2. 咬合关系

B建立人员和账户 → A完成身份会话 → D认领授课 → C注册产生占座条目 → D查询花名册 → E关闭并补位、生成最终课表 → D录入成绩 → C下一学期先修校验。

A的目录快照横向支撑C/D/E；E的学期守卫支撑C/D；B的人员状态约束C/D。每条箭头必须有契约与共同测试，避免五个人分别做互不相连的页面。

## 3. 接口契约（v1候选）

|契约|提供→消费|输入 / 输出|关键失败语义|共同验收|
|---|---|---|---|---|
|IC-01 身份|A→全员|authenticate(username,password)→Account(role,student_id,professor_id)|AuthenticationError；错误计数持久化|新增人员后可登录；删除后会话失效|
|IC-02 目录|A→C/D/E|snapshot(semester)→CatalogSnapshot|CatalogUnavailableError；只读，TTL300s|同学期冷请求合并；故障不写课表|
|IC-03 注册守卫|E→C/D|require_registration_in_progress(conn) / require_semester_open(conn)|截止与关闭明确区分|截止后学生拒绝、最终关闭后教授拒绝|
|IC-04 名额|C→D/E|schedule_item状态ENROLLED/COMMITTED算占座|SELECTED/CANCELLED不占座|花名册人数与实际占座一致|
|IC-05 历史成绩|D→C/E|grade(course_id,semester,grade)；passed_courses|只取更早CLOSED学期A–D|F/I不能满足先修|
|IC-06 关闭|E→C/D|close_registration()→CloseReport|提交前异常整体回滚|关闭后课表不可改，花名册为最终确认|
|IC-07 计费|E内部/模拟外部|send(key,student,semester,amount,payload,now)|幂等key；失败保留PENDING|接收后重发不增加发票|
|IC-08 人员删除|B→A/C/D|delete_student / delete_professor|历史引用拒绝硬删|登录、课表、授课没有悬空引用|

conn参数为事务边界的重要契约：上下游读同一写事务，不私自开独立写事务，不在事务里调用慢外部网络。

## 4. 共同联调验收门

G1 A+B：新建人员→获得账号→登录正确角色→删除无历史人员→旧会话失效。B操作，A观察账号与会话断言。

G2 A+C+D：目录由A提供，D认领课程，C学生提交，D看到花名册；先修不满足则C报错，D花名册不增加。C/D共同签字。

G3 C+D+E：无教师课程已有人选，E关闭后取消；备选按顺序补位；D花名册与C最终课表吻合。E主导，C复核条目，D复核人数。

G4 C+E：两人抢最后名额→最多10人→关闭计费→金额只含最终确认课程；容量与费用不能各用不同人数口径。

G5 A+D+E：目录离线失败不改状态；计费离线关闭成功待发；恢复后发送一次。A操作故障开关，E核对outbox，D检查课程保持可解释。

G6 B+D+C：历史成绩人员不能硬删；教授把I改B→下一学期先修通过。B说明历史保护，D录入，C验证。

## 5. 评审环与交接清单

建议评审环：A审E；E审C；C审D；D审B；B审A。核心模块同时邀请消费者审查。

每次交接含：函数签名、字段/枚举、输入校验归属、事务拥有者、异常类型、幂等性、测试数据、至少一正一负用例、文档位置。接口变化先修改契约，拉提供方和消费方一起改测试。

## 6. 可量化贡献与实际记录

建议评价维度：需求与设计20%、实现30%、测试25%、集成/评审15%、文档/答辩10%。每项证据绑定需求编号、真实提交/文件、评审记录、测试结果。组长汇总后由五人确认，总和100%。遇到某人只写总结不参与接口与测试，应重新分配任务以弥补参与，而非人为均分。

实际记录模板：日期｜成员｜FR/IC编号｜操作与决策｜证据路径/提交号｜评审者｜耗时｜遗留问题。当前没有代填真实姓名、出勤、签名和已完成贡献。
