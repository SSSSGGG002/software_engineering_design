# 答辩指南与演示脚本

## 1. 10–12分钟五人串讲

A（2分钟）：题目边界、8用例、需求差异、分层单体；展示架构和只读目录。
B（1.5分钟）：人员建档→账号生成→历史删除保护；解释数据一致性。
C（3分钟）：草稿不占座→提交检查→版本冲突/最后名额；展示测试证据。
D（2分钟）：授课认领→花名册→成绩→下一学期先修，解释对象归属。
E（2.5分钟）：截止→关闭→补位/取消→计费离线恢复；解释本地事务与外部最终一致。
全员留1分钟回答贡献与质量核验问题，依据真实记录回答。

## 3. 推荐主演示（6分钟）

1. 学生s1登录→编排课表：首选201程序设计、210高数、211线代、204导论；备选213离散、207网络。先保存，检查SELECTED；再提交，四首选ENROLLED、两备选SELECTED。211原来9人，此时达到10人。
2. s18新生尝试205算法，因未通过CS102拒绝且不建课表；尝试211线代，提示满员。通过课表页面展示后台校验，勿只展示前端下拉框。
3. 教授p1查看201花名册，有s1及原有新生。p2尝试访问p1花名册返回权限错误；自动化证据可替代现场手工篡改。
4. 注册员在周期页直接关闭：未截止时被拒。将计费切离线→勾选结束加退选→确认关闭。
5. 展示204无教师被取消；213备选按顺序补入且不超过10人；不足3人的课程取消；最终可能少于4门，这符合单轮关闭口径。
6. 查看发件箱PENDING→恢复计费在线→立即重试→SENT。再次重试不增加账单。将“业务关闭成功”和“外部投递稍后成功”分别说明。
7. 教授p1在最新已关闭秋季201录入s1成绩B；学生s1再次确认密码后查看秋季成绩。说明教学结束日期是当前待改进口径。

## 4. 独立异常演示

- 双窗口：s18两页打开同一草稿；一页保存后另一页提交旧version，提示刷新，第一份结果保留。
- 精确并发：运行pytest中的test_last_seat_concurrency。两个线程由Barrier同时释放，结果一成功一拒绝，数据库人数10。浏览器快速点击无法证明真正竞争，自动化断言更可靠。
- 目录离线：注册员关闭课程目录开关会清空缓存；学生打开编排页返回503；恢复在线重新进入。已有缓存仍可在TTL内服务的情况由集成测试验证。
- 历史删除：注册员尝试删除s1或p1，显示历史引用保护；新增无历史人员可以删除。
- 原子回滚：展示test_close_rolls_back_internal_failure，故障注入在账单构建点，验证学期、开课、发件箱都没有部分更新。

## 5. 常见追问与回答要点

**为什么用Flask和SQLite？** 五人课设需要可运行、可讲清；课程允许自由选型。显式SQL和事务方便讲解不变量。写事务串行造成容量上限，2000/500要求尚未达标验证。

**软件工程体现在哪里？** 来源可追踪的需求→用例与领域模型→接口契约→分层实现→分级测试→缺陷回归→配置基线；每项成果关联可验收证据。

**Course与Offering有什么区别？** CS101是课程，2026秋CS101-01是开课；选课、教授、容量关联开课，先修关联课程。

**缓存会不会超卖？** 只缓存课程静态目录；名额实时读取本地条目，在同一写事务检查并写入。

**为什么前端检查后后端还检查？** 浏览到提交之间名额可能变化；JS只能提示，数据库事务才保证原子性。

**为什么一个失败就全部回滚？** 原用例后置条件要求失败时状态不变；先退旧课再加新课若无事务会丢失原名额。

**为什么同时用事务和version？** 事务防止跨用户名额竞争；version防止同一用户两个页面的陈旧覆盖。解决不同问题。

**关课为何只补位一次？** 按原文步骤2→3→4单轮实现；补位后仍不足3人的课程取消，不承诺每人最终4门。反复优化是需求变更。

**为什么无教授课程也允许学生先选？** 教授认领和学生选课在注册期内可并行；最终关闭用例明确取消无教授开课。

**发送账单失败为什么不回滚注册？** 本地事务与外部系统没有共享原子提交；同事务持久化发件箱，再重试幂等发送。这样可恢复且不会把长期外部故障持有在数据库锁内。

**重复发送如何保证？** key=学期:学号，接收端唯一键去重；发送可能至少一次，业务账单效果幂等。不能声称网络调用恰好一次。

**成绩安全怎么做？** 登录角色、任课归属、学生身份从会话、成绩再次确认、no-store；没有做复杂安全平台。真实部署仍需HTTPS和强密码等基础运维。

**测试覆盖率高就一定正确吗？** 不是充分证明。应看边界、状态、并发与故障断言；未测Windows、大容量和长期可用性如实列出。

**五人如何协作？** 画出B→A→D→C→E→D→C闭环，举出实际IC交接、评审与失败联调修复证据。切勿把本包建议分工当成已发生事实。

## 6. 演示故障应急

登录失败：检查是否错误5次锁定，等待5分钟或使用另一演示账号；不要现场随意删库。选课失败：先核对先修/容量/时间，通常是业务拒绝，不要把失败提示隐藏。端口占用：停止旧服务，确认仅一个run.py。目录离线：恢复注册员开关。后台未重发：推荐run.py启动；CLI仅手工retry-billing。数据跑乱：停止、备份、init-demo、重启，保留一份不依赖临时操作的测试结果备查。
